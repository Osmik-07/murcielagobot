# murcielagobot

Telegram-бот, который продаёт Telegram Premium и Telegram Stars за TON / USDT
(сеть TON) напрямую через [Fragment](https://fragment.com) — без посредников
вроде CryptoBot и без собственного склада товара. Клиент платит на кошелёк
бота, бот тут же покупает подарок на Fragment тем же кошельком и отправляет
получателю.

Живой пример: **[@murcielago_nebot](https://t.me/murcielago_nebot)**, задеплоен на
`murcielagonebot.ru`.

## Как это работает

```
клиент → бот (aiogram) → живая цена с Fragment (+ наценка)
      → счёт в TON Payment Tracker (tonconsole.com), уникальная сумма
      → клиент платит на кошелёк бота
      → TonConsole webhook → бот проверяет статус АВТОРИЗОВАННЫМ запросом
      → покупка на Fragment (подпись транзакции локально, seed-фразой)
      → товар у получателя, клиенту приходит подтверждение
```

Интеграция с Fragment — через неофициальную библиотеку `fragment-api-py`
в Full-режиме: сессия получается чистой TON-proof подписью кошелька
(без Telegram-логина, без QR-кодов), поэтому весь путь от оплаты до выдачи
товара работает без единого ручного подтверждения.

## Почему это не просто CRUD-бот

Основная инженерная задача здесь — не диалог с клиентом, а то, что происходит
между оплатой и покупкой: выдачу товара могут одновременно попытаться
запустить три независимых источника (вебхук TonConsole, кнопка «я оплатил»
у клиента, фоновая джоба сверки), а купить на Fragment можно только один раз
за один платёж.

- **Идемпотентность без блокировок.** Переход заказа между статусами —
  это один условный `UPDATE ... WHERE id = :id AND status = :expected`.
  Postgres на READ COMMITTED сам сериализует конкурентные попытки: та, что
  обновила ноль строк, молча уходит. Один вызов реально покупает на
  Fragment — остальные видят чужой прогресс и просто ждут результата.
  (`db/repository.py::claim_order`)
- **Отдельный статус `fulfilling`** на время самой покупки — право «сходить
  на Fragment» разыгрывается атомарно, отдельно от факта оплаты. Если
  процесс упадёт посреди покупки и станет неизвестно, ушла транзакция в
  сеть или нет, заказ **намеренно** не повторяется автоматически — это
  единственный безопасный выбор, когда цена ошибки — оплатить товар дважды.
  Дожимает такие случаи только человек, разбуженный алертом.
  (`services/fulfillment.py`)
- **Источник правды об оплате — один.** Тело вебхука не проверяется на
  «оплачено или нет» — это лишь сигнал «сходи перепроверь конкретный
  инвойс». Решение всегда принимает авторизованный `GET` статуса у
  TonConsole. Это делает эндпоинт безопасным даже без проверки подписи
  запроса: подделать можно «дёргай меня почаще», но не сам факт оплаты.
- **Деньги — только `Decimal`.** Цена приходит от Fragment строками,
  наценка и уникальный «хвост» суммы (чтобы разные заказы по одной цене не
  схлопывались в один платёж на общий адрес) считаются в фиксированной
  точности вплоть до минимальной неделимой единицы TON/USDT.
  (`services/pricing.py`)
- **Один функциональный путь выдачи** для вебхука, кнопки и джобы сверки —
  `services/fulfillment.py::process_order_payment`. Ни у одного из трёх
  триггеров физически нет своего кода покупки.

## Стек

`aiogram 3` · `SQLAlchemy 2 (async)` · `PostgreSQL` · `Redis` (FSM) ·
`aiohttp` (вебхук) · `APScheduler` · `structlog` (JSON-логи) · `fragment-api-py`

## Структура

```
bot/       — диалог с клиентом: хендлеры, клавиатуры, конфиг, точка входа
services/  — Fragment, Payment Tracker, расчёт цены, единая логика выдачи
db/        — модели и репозиторий (SQLAlchemy 2.0, async, атомарные claim'ы)
jobs/      — сверка платежей и протухание неоплаченных заказов
deploy/    — скрипт, который на проде запускает GitHub Actions
```

## Запуск

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env   # заполнить: BOT_TOKEN, FRAGMENT_WALLET_SEED,
                        # FRAGMENT_WALLET_ADDRESS, TONCONSOLE_API_KEY,
                        # PAYMENT_TRACKER_TOKEN, DATABASE_URL

python -m bot.main
```

Postgres нужен заранее (схема создаётся сама при первом запуске). Redis
опционален для локальной разработки — без `REDIS_URL` состояние диалога
живёт в памяти процесса; заказы и деньги при этом не теряются, они в БД.

Без `WEBHOOK_BASE_URL` вебхук выключен, и выдача идёт по кнопке «я оплатил»
и джобе сверки — для локальной разработки этого достаточно.

## Прод

Systemd-юнит от непривилегированного пользователя, Caddy как reverse proxy
с автоматическим Let's Encrypt, Postgres/Redis в Docker с лимитами памяти.
Деплой — по пушу в `main`: GitHub Actions подключается по SSH-ключу, который
на сервере ограничен `authorized_keys`-командой на ровно один скрипт
(`deploy/deploy.sh`) — что бы CI ни отправил, выполнится только он.
